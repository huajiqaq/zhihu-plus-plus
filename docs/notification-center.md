# 通知中心

## 范围

列表及私信请求的参考是知乎 Android 11.3.0（40308）的实际页面与请求。卡片的区域绑定、筛选入口、快捷动作及其参数另与官方 Android 11.12.0（41208）的前端方法体核对；静态证据不等于已验证线上响应。客户端支持：

- 消息主页的四个通知分类、未读数、邀请回答入口和消息会话列表；
- 评论转发与赞同喜欢卡的正文、引用、来源和头像独立跳转；可靠评论目标的文本回复及喜欢/取消喜欢；
- 邀请回答的分页列表、日期标记、问题详情与写回答/查看已有回答入口；
- 私信会话的分页读取、消息查看和文本发送；
- 私信气泡按内容宽度分侧展示、双方头像、逐条精确时间切换和前台 5 秒轮询；
- 既有通知显示偏好、未读角标偏好和自动已读偏好。

尚不支持发起新会话、发送图片或贴纸消息、删除邀请。通知设置沿用既有入口和默认开关。

## 请求预算

原始抓包和未脱敏数据保存在仓库外，账号 Cookie、私信正文和用户标识不进入共享资料。

每个页面的首屏请求预算如下：

| 页面 | 请求 |
| --- | --- |
| 消息主页 | `GET /notifications/v3/message/v3?limit=20`，后续每页一次 |
| 邀请回答 | `GET /notifications/v3/timeline/entry/invite?invite_with_time_slice=1&limit=20`，后续每页一次 |
| 通知分类 | `GET /notifications/v3/timeline/entry/{entry}?limit=20`，后续每页一次 |
| 私信查看 | 首屏并行请求 `GET /messages/user/{peer}` 与 `GET /messages?limit=20&sender_id={peer}`，后续每页一次消息请求 |
| 私信发送 | 用户每次点击发送只调用一次 `POST /messages`，成功后直接插入服务端返回的消息，不自动二次拉取 |

启用“自动标记已读”时，时间线在列表读取成功后才对本板块调用 `POST .../actions/readall`。只有成功才把已加载行的 `is_read` 和 `unread_count` 一起更新；同轮历史分页沿用成功状态，重新刷新则以新响应为准。消息页顶栏的批量操作只针对有未读的四个分类，逐类确认；失败的分类、邀请、私信和未知板块不被顺带清除。关闭未读角标会隐藏分类、会话和通知行的红点、底色及未读语义，不改变服务端状态。

通知卡不因显示操作而预取详情。点击喜欢/取消喜欢时才请求 `POST` / `DELETE /reaction/comments/{comment_id}/like`；只有成功才切换状态。文本回复先打开输入确认框，点击发送才复用现有评论 `comment_v5` 提交，请求携带被回复评论的 `reply_comment_id`。未获得服务端评论对象不报告成功，输入保留在当前弹窗。

私信页处于 `RESUMED` 时，每隔 5 秒静默拉取最新消息；请求完成后再等待下一轮，离开前台时取消轮询。新消息超过一页时继续分页，直到遇到此前已连续同步的消息或服务端分页终点。发送成功的消息立即展示，但在列表同步补齐之前不作为停止分页的边界。合并按稳定消息 ID 去重，并通过重叠消息保留服务端顺序，包括时间戳相同的消息；历史记录与历史分页游标继续保留。轮询失败保留现有内容，不显示加载动画，也不打断草稿输入。手动刷新会使尚未完成的旧轮询响应失效。

双方气泡随内容自适应，最大宽度为消息内容列的 88%；对方头像在左，本人头像在右，本人头像复用账号页的登录资料。点击每条消息下方的时间标签，可独立切换相对时间与本地时区的 `yyyy-MM-dd HH:mm:ss`，再次点击还原。时间标签的测试 tag 为 `private_message_time_<stableId>`。

## 数据流

`message/v3` 的 `head` 提供四个分类及未读数，`column_head` 提供邀请回答入口，`data` 提供消息会话。顶层 `unread.message.count` 是消息页的总未读数。同账号首页恢复前台时，只有已登录且开启角标才重取这个总数；失败保留上次结果。不能对有分页的首屏条目求和，也不能以本地分类标读数推算总数。邀请回答和普通通知分类共享时间线模型，但各自由独立分页状态持有。私信页面使用独立的消息模型和分页状态，不与通知时间线混合。

首页消息条目可能同时携带通知分类链接和 `inbox/{peer}` 链接，优先进入私信。四个分类按 `head[].content.target_link` 的入口名或已知 ID 辨认，缺失时才回退到已核对的标题；`column_head` 按邀请标识或已知目标查找，不把第一栏固定当作邀请。主页刷新失败保留已加载内容；重试替换同 ID 的首屏行、把新行放回顶部，并保留已加载尾部。

“应用内显示”按通知的动作副标题优先匹配，标题或旧动作字段也可识别；私信会话不因正文碰巧是某种动作而被过滤。邀请通知仍按既有 opt-in 默认，主动打开的邀请列表及其导航入口不作为推送过滤。

通知主页在首次进入和每次从二级页面返回前台时重新拉取首屏，使四个分类的未读数与服务端同步。文本私信按官方客户端协议先构造包含 `receiver_id`、`content`、`content_type=0` 和 `source_type=message_list` 的 form，再加密为请求体并标明协议版本；发送失败时保留草稿，成功时清空草稿。

## 字段约定

- `column_head.avatar_urls` 是包含 `url` 与 `night_url` 的对象数组，不是字符串数组；模型按原始响应解码。
- `CommentAndForwardViewHolder` 与 `LikeNotiViewHolder` 区分 `content.target_link`（正文）、`content.sub_target_link`（引用）、`target_source.target_link`（来源）和 `head.target_link`（头像/标题）。点击缺失或已删除的区域不借用其他链接；正文内已有链接和表情仍可独立显示。
- 正文、引用、来源分别使用 `content.is_deleted`、`content.is_sub_deleted`、`target_source.is_deleted`。来源图只展示未删除的 HTTPS 知乎图片，`target_source.has_video` 表示封面上的视频标记，不表示可直接播放。
- 评论动作需要 `extra_action.data.type=comment`，并且 `data.id`、`data.resource_type`、`extra_action.resource_id` 与正文评论锚点全部一致。删除、折叠或目标不明时不提供写操作；缺少 `voting` 时不提供喜欢切换。
- 邀请卡片的奖励说明确认为 HTML 字段，只在这个已验证字段上提取可见文字。
- 已观察到的私信 `content_type` 为纯文本和带插件文本两类；未知接收类型保留降级文案，发送仅支持已验证的纯文本类型。

## Android 系统通知

系统通知与应用内显示偏好独立，四种类型默认关闭。用户显式开启时才申请 Android 13+ 通知权限；权限未授予、系统总开关或通道关闭时显示实际阻止状态。

WorkManager 在联网条件下每 15 分钟检查当前登录账号，执行时间由系统后台策略决定，不是实时推送。只读取已订阅类型对应的 `like`、`comment`、`invite` 时间线，同一时间线不重复请求；后台不调用标读、回复或喜欢接口。首次启用及新类型的第一次成功同步只建基线，不弹历史消息；沿合法的同源 `paging.next` 追到已知边界或末页，任一页失败不推进进度。

订阅、基线和一次性点击凭据存于本机 `noBackupFilesDir`，退出或切换账号会撤销当前订阅和已发布通知，不随可移植偏好恢复。通知不保存作者或正文内容，锁屏只显示通用提示。显式、不可变 PendingIntent 携带不可猜测凭据；宿主先确认账号和事件，再消费一次并打开正文、评论锚点或邀请问题。失效或跨账号点击不借用当前账号打开。

投递记录先落盘再调用系统通知，避免重试重复响铃；系统发布与本地文件不在同一事务中，若进程恰在这两步间退出，可能漏掉该条提醒。应用内通知列表仍可查看。

分类标读请求成功后，只撤回原账号在请求开始时已存在、仍然有效的同分类回执。标读失败不撤回，等待响应期间新投递的提醒不受影响。点击单条系统通知不会将整类消息标为已读。

## 桌面与 iOS

桌面与 Apple 宿主复用相同的分类、首轮静默基线和一次性点击回执，四种类型均默认关闭。应用内通知页和未读角标不依赖系统授权。能否订阅取决于实际宿主、系统通知服务及点击入口。

| 宿主 | 检查时机 | 投递和点击 |
| --- | --- | --- |
| Linux 桌面 | 进程运行期间 | 使用本机会话总线的 `org.freedesktop.Notifications`；服务须支持 actions，当前连接方式为 `unix:path`。点击请求唤醒原窗口；进程退出后不能从通知恢复。 |
| macOS 原生 `.app`、iOS | 应用能运行时 | 启动时安装 `UNUserNotificationCenter` delegate，显式开启时请求权限。已发布通知的点击等待账号和导航就绪后消费。挂起或退出后不保证继续检查，不是 APNs。见 [iOS 宿主](../iosApp/README.md)。 |
| Windows x64，正式签名安装的可选 MSIX | 进程运行期间 | 包内原生宿主用 WinRT 投递通知，点击只传一次性回执。Windows 可为已投递通知激活应用，待账号和导航就绪后打开目标。关闭应用期间不会检查新消息。 |
| Windows 普通 MSI、直接运行 JVM | 不启动系统通知检查 | 没有相应的包身份和激活入口，只提供应用内消息。安装或更新普通 MSI 不需要额外注册。 |

在「消息 → 通知设置」查看本机可用性。系统接受提交通知，不等于用户已看到：勿扰设置、通道和桌面窗口管理器都可能影响显示或聚焦。

## 尚未接入

11.12 的评论、赞同和收藏分类通过 `BaseNotificationFilterFragment` 展示“全部消息 / 我关注的人 / 关注我的人”。选择会触发 `BaseEntryNotificationFragment.onRefresh`，经 `q.y.B0`、`repositories.w.q` 到时间线服务的 `filter_type` 参数。已确认这不是本地文本筛选；两种非默认选择对应的实际请求值未从允许的明文业务证据中确认，因此不发送猜测参数，也不显示不能生效的菜单。

想法卡的评论、反应与评论项的回复、喜欢是不同分支，不能共用评论 ID 或混用反应状态。本实现只接入上述可交叉核对的评论动作，不提供想法行内反应、服务端通知删除或媒体播放按钮。没有接入厂商实时推送或私信媒体发送；各平台本机提醒的运行条件见上表。
